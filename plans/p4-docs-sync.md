## 2. 工作項目

### 2.1 補齊 `CHANGELOG.md`

- 每個缺少的版本一節，放在 V0.14.0 與 V0.5.0 之間，依版本倒序排列。日期用該 commit 的 author date，取自 `git log -1 --format=%ad --date=short <sha>`。
- 文風沿用既有條目：繁體中文，第一段寫版本主題，接著是重點條列。每個版本都要寫清楚三件事：
  - 玩法或計分是否改變；
  - 榜單 ID 的變化：v2 到 v3 發生在 V0.13.0；
  - 存檔鍵或格式的變化：雲端存檔從 V0.8.0 開始。
- 內容只能來自 commit message、`git show --stat` 與實際 diff，不可臆測。不確定的寫法要明確標示。
- 每節控制在 5–12 條。細節指向 `docs/` 與 `PERFORMANCE.md`，不複製整份規格。

### 2.2 重寫 `RELEASE.md`

- 改成目前交付版本（寫作時是 0.14.0；P2 或 P3 若先發布就用最新版本）。舊的 0.11.0 內容已移到 CHANGELOG，這裡不再保留。
- 依平台規格的完成報告格式，分成以下段落：
  1. 遊戲 ID、版本、tag、成品位置（`game.zip`）
  2. 本版變更摘要（連到 CHANGELOG）
  3. 相容性：榜單 ID、存檔鍵、`cloudSave` 格式、`devices`
  4. 驗證狀態，必須分開寫：程式碼完成、自動化測試、ZIP 驗證（tools 1.2.0）、GitHub Release、平台上架。沒做過的寫「未驗證」。
  5. 發布前手動驗收清單：iframe sandbox 實測、`scripts/test-perf-stress.mjs`（P2 完成後才有）、提示流程（P3 完成後才有）
- 不寫入量化宣傳數字，除非有本版的量測報告可以對照。

### 2.3 更新 `plans/README.md`

- 移除失效的 `file:///F:/...` 連結，改用相對路徑。
- 新增「目前工單」段落，列出 P2（`p2-performance-regression.md`）、P3（`p3-onboarding-readability.md`）、P4（本文件），寫明狀態與並行界線。
- 把 `01`–`05` 與 `wp-01`–`wp-05` 標為「v0.0.x 時代的歷史設計」，內容大多已實作，且參照已移除的 `game.js`。保留檔案，不刪除。
- 「候選後續」列出 P1 數據指出但沒有處理的事項，供日後排程：
  - 共鳴集中在 kinetic：其他流派平均只有 0.4–1.8 張。
  - 開放大地圖模式下 Breacher、Vanguard、COLOSSUS 通關率明顯偏低。
  - COLOSSUS 仍比其他武器低約 20 點，主因是蓄力減速。
  - 首領擊殺時間遠低於數值表的目標。
  - domino 與 execution 讓 `maxCombo` 顯示超過 35。

### 2.4 標記 `PLAN.md` 為歷史文件

在檔案頂端加一段說明：本文件是 2026-09 的初期計畫，增量 01–15 已全部完成；目前的計畫在 `plans/`。原文不改。

### 2.5 Tag 缺口（只記錄，不動作）

- 在 `RELEASE.md` 的附錄記錄 v0.5.0、v0.12.0、v0.13.0 沒有 tag 的原因。
- 不建立、移動或補打 tag。平台規格禁止移動既有 tag，補打舊 tag 也需要使用者明確授權。

## 3. 修改檔案

`CHANGELOG.md`、`RELEASE.md`、`plans/README.md`、`PLAN.md`。不改 `ARCHITECTURE.md`：它的維護規則禁止寫入版本記事。

## 4. 驗收

1. 版本號、日期與 commit 對照逐一核對。附一張「版本 → commit → 日期」表給審閱者，表放在 PR 或 commit 描述，不放進 CHANGELOG。
2. `RELEASE.md` 的每個驗證狀態都有出處（測試輸出或「未驗證」）。
3. `plans/README.md` 的所有連結在 repo 內都能點開。可用一行腳本檢查 `](` 後面的相對路徑是否存在。
4. 沒有修改任何遊戲成品檔。`git diff --stat` 只會出現上述 4 個文件。
5. 不 push、不打 tag、不發布，除非使用者明確授權。

## 5. 順序

建議在 P2 與 P3 完成後再做，CHANGELOG 和 RELEASE.md 可以一次寫到最新版本。若要先做，2.1、2.3、2.4 可以立即進行，2.2 等最後一個版本確定再寫。
